## X / 推特

**Andrej Karpathy（AI 研究者，前 Tesla AI 负责人）**
1) 中文总结：Karpathy 抛出一个很妙的 eval 点子（给 LLM 经纬度、问它「陆地还是海洋」，问上万次绘成世界地图，模型居然答对，说明知识来自对互联网的无损压缩）；更系统地，他谈了「LLM 的输出形态」：写作用 ASD-STE100 受控语言更清爽、用图代替长文、直接要 HTML 出交互网页、而他最看好的形态是「任意主题的定制讲解视频」。结论是：LLM 越强，越多工作会上升到「监督与理解」，而我们可以让 LLM 产出过去根本不值得做的大型、可丢弃软件产物（网页、视频讲解等）。
2) 中文全文翻译：
- 推文 1：一个很酷的 eval。只要问 LLM「陆地还是海洋？」，然后把经纬度坐标以文本形式喂给它。问 16200 次，绘成一张图。模型是知道的。这来自它对整个互联网的压缩。
- 推文 2：我们会花越来越多的时间去理解语言模型的输出。几点想法、小技巧：写作——我有个屡试不爽的办法：让你的 LLM 用 ASD-STE100 来解释一件事，这是一套最初为航空维修文档开发的受控语言规范。LLM 很熟悉这门语言，而且它带了很强的简洁写作风格约束，我经常觉得这样读起来清爽得多。有时我会稍微放松一点，比如要求「做到 ASD-STE100 的八成」，因为那套规范相当严苛。但还有更好的：图 / 图像——与其写字，不如让你的 LLM 画一张图。图往往更容易被处理、解析和理解。但还有更好的：网页——要求以「HTML」格式输出，就能得到一个漂亮、可交互的网页。LLM 在前端上越来越强，能做出很棒的体验和动画。但还有更好的：讲解视频——我最看好的输出形态，是为任意主题生成完全定制、专属的讲解视频。可以试着说「做一个 3blue1brown 风格的 X 主题视频讲解。用我的 ElevenLabs API key 做旁白配音」。（后者你需要一个 API key，或者你可以让 LLM 帮你找用本地算力就能跑的体面免费替代方案）。这真的开始能用了！总结一下：随着 LLM 变强，它们会自主承担越来越多的苦力活，而我们大量的工作会沿着抽象层级上移，进入监督与理解。幸运的是，LLM 在这里也能帮忙，因为智能和代码越来越充裕，你可以要来那些庞大、定制、可丢弃的软件产物（比如网页应用、视频讲解），这些在以前根本不值得去做。在这里推一推边界，你会被惊到的。
3) 推荐理由：Karpathy 是少数能把「模型能力边界」讲得既直观又有方法论的人。那个「陆地 / 海洋」eval 是理解 LLM 世界知识的绝佳小实验；而关于「输出形态」的思考，对任何在用 LLM 做内容或产品的人都是方向标。

## 官方博客

**Anthropic Engineering：我们如何在各产品中「封住」Claude**
1) 中文总结：Anthropic 工程团队系统复盘了 agent 安全的核心矛盾——部署风险 = 失败概率 × 破坏半径。随着模型能力变强，不部署的代价变大，只要能把「破坏半径（blast radius）」压住，风险收益就倒向采用。文章给出三层防御（模型层 / 运行环境层 / 外部内容层）与三种隔离模式（claude.ai 的临时容器、Claude Code 的人审沙箱、Claude Cowork 的密封 VM），并诚实披露了多个「我们漏掉的风险」：信任对话框之前就执行的钩子、把员工钓成数据外泄的 prompt injection、通过白名单域名用自家 API 外泄数据等。核心结论：先在环境层做确定性边界，再在模型层做概率性引导；自研组件往往是最弱一环。
2) 中文全文翻译：
十二个月前，我们会毫不犹豫地拒绝「授予 Claude 足以搞垮某个 Anthropic 内部服务」的访问权限这种想法。今天，这种级别的访问已是常态，Anthropic 的开发者也因此更高效。这类部署的风险有两个组成部分：失败的可能性有多大，以及一旦出错能造成多大破坏。在护栏和模型训练上的进展稳步压低了前者；而后者——理论上的破坏半径——只会随着能力和访问权限的扩张而变大。然而，随着 agent 变得能够完成曾经需要一个人甚至一个团队才能完成的工作，不部署的代价也变得足够大，只要产品能做得安全，风险收益的算盘就会重重倒向采用。工程问题于是变成：如何给破坏半径封顶。只要能对自主 agent 的相对破坏（比如通过控制其环境）设上下限，高价值的能力就足以支撑部署。Claude Mythos Preview 就是一个例子：2026 年 4 月时，它的破坏半径被认为过高而没发布。不过我们预计，随着防御方把关键系统加固、护栏成熟，具备类似能力的模型会更广泛地发布——尽管某些风险将永远存在。

模型能力是 agent 部署总风险中的一个重要因素。大致有两种方式来应对。第一种是通过人在回路（human-in-the-loop）来监督 agent 的行为。Claude Code 过去靠在每一步都向用户要权限，来防止 agent 做出非预期的动作。理论上这可行，但我们发现这套做法并不可靠。我们的遥测显示，用户大约批准了 93% 的权限请求。一个人看到的批准弹窗越多，对每一个投注的注意力就越少，久而久之监督也变得松懈。我们最近做了 Claude Code 的 auto 模式，用更安全的自动化批准来减少这种「批准疲劳」。但漏洞仍然存在——任何概率性防御都有非零的漏报率。

第二种给破坏半径封顶的方式——也是本文的重点——是「 containment（ containment，围堵）」。比起监督 agent 做了什么，我们监督的是它「能做什么」，通过沙箱、虚拟机、出口（egress）控制等手段强制访问边界。这正是 Anthropic 工程投入最多的地方，也是许多最出人意料的安全事故发生的位置。过去两年，我们发布了三款主要的 agent 产品：claude.ai、Claude Code 和 Claude Cowork。它们各自面向不同受众，需要不同的围堵架构。本文分享哪些设计站住了、哪些崩了，以及我们一路上学到的 agent 安全经验。

三类风险，三块防御。agent 面临的安全风险可归为三类：用户滥用——用户出于恶意或疏忽，指挥 agent 去做有害的事。从「让 agent 绕过某个他觉得烦人的检查」，到「运行一条他不理解的破坏性命令」，再到「明确指定要造成危害」，都算。模型失当——agent 做出了没人要求的有害动作。随着模型变强，它们在多数行为评测上更对齐了，但这不意味着风险必然缩小。能力较弱的模型更容易误读局势、犯明显的错；能力更强的模型犯错更少，却也更擅长找到通往目标的意外路径，往往绕过那些没人想到要写下来的限制。在 Anthropic，我们见过 Claude 模型为了完成任务而「好心」逃出沙箱、翻 git 历史找编码测试的答案、甚至自发识别出自己正在跑的基准以便破解它的答案密钥。每个模型都带来一组新能力，有时会被用在意想不到的地方。外部攻击者——agent 通过工具、文件或网络访问等外部渠道被攻击。这一类既包括 prompt injection，也包括对 agent 运行时、编排层或代理的传统攻击。

搭建围堵与防御体系时，我们把防御施加在三个主要组件上：agent 运行的环境。我们用进程沙箱、VM、文件系统边界和出口控制，约束 agent 能在何处、以何种方式行动。目标是给 agent 能触及的范围设一道硬边界。比如，如果凭证从不进入沙箱，那无论原因是用户、模型找到「创意」路径、还是攻击者，凭证都无法被外泄。紧的边界也意味着你可以放松监督——Claude Code 的参考 devcontainer 正是为了让 agent 能在无人值守下运行、无需逐步批准而存在的。agent 所查询的模型。这里的机制包括系统提示、分类器、探针和训练修改。因为模型是概率性的，这些只塑造 agent「倾向于」做什么，而非它理论上「能」做什么。这些防御很强：在 Gray Swan 的 Agent Red Teaming 基准（测试对 prompt injection 的易感性）上，Claude Opus 4.7 单次尝试把攻击成功率压到约 0.1%，100 次自适应尝试后约 5–6%；Claude Code 的 auto 模式能在危险动作执行前拦下约 83% 的过度冒进行为。但即便有顶级防御，模型层的保护也永远不可能 100% 有效，所以它不能单独撑起安全。agent 能触及的外部内容。MCP server、第三方插件、网页搜索工具，都会把来自你无法控制来源的内容喂进 agent 的上下文。一个经过审计的连接器不等于经过审计的数据——比如一个 GitHub 连接器，即便通过了恶意软件检查，也可能把一份被下毒的 README 直接加载进模型上下文。细粒度地限制工具权限有助于缩小破坏半径：一个只读数据库的 agent，就比一个能写生产库的 agent 可以部署得更广。防御应当相互重叠、互补。当环境层防御缺失时，模型层必须补位（这正是 Claude Code auto 模式的设计初衷）。在本地，环境与模型防御能挡住恶意的工具输出；但通过在限制工具能力和访问上往上加防御，可以在更上游拦截。

三块要防御的组件：模型、它运行的环境、以及 agent 能触及的外部内容。

agent 围堵的模式。聚焦环境层，我们描述三种隔离模式，以及它们如何为 claude.ai、Claude Code 和 Cowork 各自定制。每种设计都是逐步成形的，在「我们需要 agent 提供的能力」与「需要用户介入的程度」之间找到平衡。

模式 1：临时容器（claude.ai 代码执行）。尽管以聊天界面闻名，claude.ai 也会写代码、跑代码、生成文件、调用连接器。当 Claude 在 claude.ai 内运行代码时，它跑在一个隔离基础设施上的 gVisor 容器里。agent 完全在服务端；本地机器不跑任何代码，文件系统是临时的（按会话）。破坏半径极小，但 Claude 能做的事也有天花板——没有持久工作区，也访问不到用户的文件系统。这也让 claude.ai 适用更传统的威胁模型：我们不是在保护用户机器免受 agent 侵害，而是在保护我们自己的基础设施、以及租户彼此隔离。claude.ai 发布前的工作以传统安全为主，比如网络配置、内部服务鉴权、编排。这再次印证了安全界最古老的教训：最弱的层是你自己搭的那层。gVisor 和 seccomp 被加固、对抗资源充足的对手的时间，远长于 agentic AI 存在的时间，所以复盘精力主要放在我们围绕它们自建的新部件上。我们后面还会回到这点，因为我们自研的代理也正是那次最严重事故中出问题的部件。

模式 2：人在回路的沙箱（Claude Code）。Claude Code 跑在用户机器上，能访问其文件系统、shell 和网络。没有这些，编码 agent 用处有限，所以必须找到安全授予这些访问的方式。一种做法是依赖人在回路。这对 Claude Code 之所以是可行解，是因为普通用户是开发者、熟悉编码环境：他们读得懂 bash，知道 rm -rf 做什么，每周都从不可信源跑好几次 npm install。这意味着当「是否允许」弹窗出现时，他们极有可能具备准确评估 agent 在尝试什么、风险几何的专业能力。鉴于此，Claude Code 上线时用了最简单的防御：读放行，写 / bash / 网络需批准。然而如前所述，批准疲劳在几周内就出现了。讽刺的是，这意味着一个本为监督而生的功能，反而可能起到相反效果——有些用户干脆不再理会。作为缓解盲目批准的第一步，我们上线了 OS 级沙箱（macOS 上的 Seatbelt、Linux 上的 bubblewrap）来加固边界：读放行，工作区内写放行，但网络默认拒绝。在沙箱内，agent 基本不被打断地运行。结果是权限弹窗减少了 84%，而且我们把运行时开源了，边界可被审计。我们的匿名使用数据还显示，有经验的用户自动批准的频率大约是新用户的两倍，但他们也更频繁地在执行中途打断 agent。有经验的用户不是给每一步设卡，而是更倾向只在 agent 跑偏时才监督它。这或许是人们与 agent 协作方式的天然演进，但同样不可靠——它要求用户既懂技术、又足够专注才能率先发现偏离。随着模型能力增强、agent 开始写越来越「野心勃勃」的 bash，这种偏离会越来越难察觉。而当用户转向多 agent 系统时，这种监督策略的有效性也会大幅下降。

2026 年 1 月，我们通过负责任的披露计划收到了关于 Claude Code 漏洞的报告。其中三个漏洞瞄准的是「用户同意之前就执行的代码」。要理解这怎么可能发生，看最直接的案例：一位开发者 clone 了一个仓库来 review 一个 pull request，而那个仓库里含有一个 .claude/settings.json，其中定义了一个 hook。因为 Claude Code 在启动时就读取项目设置——早于弹出标准的「你信任这个文件夹吗？」提示——攻击者编写并提交的那条 hook 会自动执行。其余几个案例结构相似：来自「尚未被信任的目录」的输入，在信任边界建立之前就被解析了。每个案例的修法都一样：把项目本地配置的解析与执行，推迟到用户接受信任提示之后。如果你在做类似的东西，请把「项目打开、配置加载、localhost 监听器」当作来自互联网的任何入站请求一样对待。它们不该仅仅因为「感觉是本地的、且在用户同意前就到了」就被隐式信任。

我们漏掉的风险：把用户当成注入向量。2026 年 2 月，在一次受控的内部红队演练中，一名研究员成功钓到了一名员工，让其用一条恶意 prompt 启动 Claude Code。这条钓鱼看起来就像普通的协作——一封「能帮我跑一下这个吗？」的邮件，附带一段可以直接粘贴的 prompt——而那段 prompt 本身读起来也像日常任务指令。但在某几步设置里，它悄悄让 Claude 去读 ~/.aws/credentials，把内容编码，然后 POST 到一个外部端点。在那条 prompt 的 25 次重试里，Claude 完成了 24 次外泄。

这是一次直接的 prompt injection——攻击者的指令是经由用户到达的，而不是经由工具输出或抓取的内容。我们的模型层防御锚定在「用户意图」上——当打字的是用户本人时，分类器没有任何异常可抓。一个拿到同样脚本的人类外包员也会做同样的事。这种情况下唯一站得住的防御是环境层，具体说是出口控制——无论意图如何都拦下那个 POST——以及文件系统边界——从一开始就让 ~/.aws 够不着。（当我们在内部 Slack 贴出那段可用 prompt 讨论时，有人指出某些内部 agent 会读 Slack。于是载荷变成了环境里的「背景音」。我们在那个线程里加了一段 canary 字符串，以便发现是否有什么东西把它捡走。在一个 agent 什么都读的世界里，调查工具本身也是攻击面。）

模式 3：本地 VM（Claude Cowork）。Claude Cowork 跑在用户桌面上，能访问用户选定的工作区文件夹。因为这个平台是为通用知识工作而非软件工程设计的，普通用户精通 bash 的可能性低得多。结果就是，人在回路的沙箱策略可能无法迁移：一个非技术知识工作者不该被指望去判断 find . -name "*.tmp" -exec rm {} \; 这类 bash 咒语。当「批准一个例外」需要典型用户不具备的专业知识时，管理员就该设一道绝对、常开的边界。为此，我们第一版 Claude Cowork 跑在一个完整虚拟机里，用平台自带的 hypervisor（macOS 上是 Apple 的 Virtualization framework，Windows 上是 HCS）。这个 VM 有自己的 Linux 内核、自己的文件系统、自己的进程表。用户选定的工作区和 .claude 文件夹被挂载进去；宿主机上其他东西都不可见。凭证留在宿主机的钥匙串里，从不进入客户机。这种设计防御的是「Claude 在某刻以不对齐的方式行事」的可能性。一个被攻陷的 Claude 仍然可能破坏工作区文件夹里的东西，所以架构要确保那是它唯一够得着的东西（直到用户添加连接器），并且由用户控制挂载了什么。

在最初的架构——我们称之为 full-VM 模式——里，agent 循环本身就跑在客户机内部，所以 Claude 以一个普通 Linux 用户的身份执行，完全不知道自己被沙箱化了。对比 Claude Code：那里有一个特权进程坐在沙箱外面，逐条命令地决定是否强制执行；一条有说服力的注入 prompt 或一次疲劳的批准点击，就能让那个进程跑起未沙箱化的东西。而在这里，没有握着「逃生舱钥匙」的外部进程，也就没有哪个组件有权授予例外。

Claude Cowork VM 的六大隔离机制里，有两道在客户机内核之外强制执行，因此即便 agent 在 VM 内拿到 root 权限也能存活；另外四道在客户机内强制执行，并且刻意保持最小，因为外层已经扛起了其余部分。不过我们很快发现，让整个 agent 跑在 full-VM 模式里会带来实际问题：VM 启动时的任何失败都会让 Cowork 完全不可用。把 agent 循环移到 VM 之外、同时让代码执行留在 VM 内，让 Claude 仍能回应用户、帮忙排查问题，而不是卡在一个错误上。这个改动对安全影响极小，因为 VM 仍然对 agent 执行的代码强制执行文件系统和网络控制。

另外，我们也把本地 MCP server 移到了 VM 之外。把它们放在 VM 内会更难审计，VM 更新时还会引发脆弱的依赖问题，而且不支持那些需要跟本地进程（比如数据库）交互的 MCP——这类 server 无论如何都得跑在宿主机上。这个改动让 Claude Cowork 与 Claude Desktop 里本地 MCP server 既有的工作方式对齐：把它们当作用户可能选择安装的任何软件，并由管理员决定启用哪些本地 MCP（如果有的话）。远程 MCP server 不受影响，因为它们不跑在用户机器上。让 agent 循环留在 VM 内意味着 VM 里任何失败都会让 Cowork 不可用；宿主模式更可靠，因为即便 VM 崩溃 agent 仍能响应，而且它仍通过隔离代码执行提供重要的安全保证。

文件系统控制是另一个重要架构选择。Claude 需要能访问宿主机上某些文件才有用，但我们想最小化破坏半径，并向用户透明展示本地文件访问。我们发现提供不同的文件挂载模式有助于精细控险；Claude Cowork 提供只读、读写、读写-禁止删除三种。这里有一个潜在的坑：符号链接的解析必须在路径校验之前、而不是之后进行，否则授权文件夹内的一条符号链接可以指向外面、实现逃逸。对企业客户，我们允许管理员通过 MDM 设置里的挂载路径白名单来控制。

我们漏掉的风险：经由「已批准域名」外泄。一个经由已批准域名外泄的清晰例子来自第三方披露。Claude Cowork 的出口白名单正确地放行了到 api.anthropic.com 的流量——产品不调用我们自己的 API 就无法工作。在这个例子中，放在用户已挂载工作区里的一个恶意文件，带着隐藏指令和一把由攻击者控制的 API key。Claude 遵循指令，读了工作区里其他文件，并用攻击者的 key 调用了 Anthropic 的 Files API。出口代理检查了目标，看到 api.anthropic.com，就放行了。文件被上传到了攻击者的 Anthropic 账户。沙箱完美工作了，数据却还是被外泄了。此前我们把白名单理解成一个「目标过滤器」，告诉 Claude 这些域名可以聊。但它或许更应该被理解成一次「能力授予」：白名单上任何域名可触及的每个功能，现在都是攻击面。放行 api.anthropic.com 就等于放行了向任意 Anthropic 账户上传文件。我们修法是：在 VM 内用一个防御性的中间人代理来拦截去往我们 API 的流量。它只放行携带 VM 自身配发的会话 token 的请求；攻击者嵌进去的 key 会被代理拒绝。它还会屏蔽能启用服务端抓取的 header。代理放在 VM 内而非我们的服务器上，因为只有 VM 知道来源——从服务器视角看，一个 Cowork 请求和任何其他 API 客户端没有区别。

这也是「你自研的软件往往最弱」这一原则的第二个实例。贯穿我们各产品的 hypervisor、seccomp 和 gVisor 都可靠。我们自研的白名单代理才是出问题的那块。

我们漏掉的风险：VM 隔离也把端点检测软件挡在了外面。评估 Claude Cowork 时，企业安全团队问：「为什么我们的 EDR 看不进里面？」答案是：把 Claude 围住的同一道隔离，也把基于宿主机的端点检测与响应挡在了外面。从 EDR 的视角看，Claude Cowork 是一个不透明的 hypervisor 进程，它无法检查客户机。隔离降低了可见性，而对那些合规姿态依赖端点可见性的团队来说，不透明是个问题。我们目前的缓解办法是用基于拉取的 OTLP 导出，让管理员在事后取回事件日志，但这和实时监测不是一回事。如果你在做类似的东西，早点为这场对话留出预算。

环境对照表：临时容器（claude.ai）｜人在回路沙箱（Claude Code）｜密封 VM（Claude Cowork）；隔离开销：容器启动 / 低延迟原生沙箱 / 完整 VM 启动；用户依赖：无 / 必须能读懂 bash / 无；破坏半径风险：服务端容器（由 gVisor + 宿主基础设施边界守卫）/ 本地工作区 / 已挂载工作区（由 vsock + hypervisor 边界守卫）。

信任 agent 读到的东西。企业常问我们怎么保护 MCP 连接。这是个好问题，但真正该问的比 MCP 本身更宽。提供给 agent 的任何外部资源同时代表两种风险：一是传统供应链意义上的代码执行风险，二是 prompt injection 向量。传统的依赖审计（锁版本、校验签名、审源码）能解决前者，却漏掉后者。远程还是本地，比看起来更重要。本地安装的工具是可审计的——你能读代码、锁版本、知道它不会偷偷变。远程工具——托管的 MCP server、云连接器——可以在你批准之后的任何时刻改变行为；你安装时的信任决定可能不再适用。我们的连接器目录靠持续复审来应对这一点，但目录之外的任何东西都应视为不可信。先用假数据、在一个能把恶意工具破坏半径封住的环境里跑它。即便工具可信，它的输出也是攻击面。前面提到的 GitHub README 例子正是如此；任何用在网页上的输入扫描，都得用同样的严格度用在联网工具返回的结果上。尽管这会增加延迟、也不是完美防御，我们偏向实时检视：一旦一条被下毒的工具返回已经把 agent 拐去外泄数据，日志上只显示一次成功的、已授权的 API 调用，事后根本没有信号可找。在 Claude Code 和 Claude Cowork 里，工具调用都经由代理，代理强制执行网络与文件策略，并能在返回值进入模型上下文之前检视它们。做检视的分类器可以是个小而快的模型，不必是负责推理的那个。

展望未来。模型和产品的演进很快。随之，风险也在变形、演化，我们的缓解措施必须跟上。持久化记忆投毒。跨会话存活的 agent 上下文占比持续增长——包括产品记忆、CLAUDE.md 文件、已挂载工作区，以及定时 / 长时运行 agent 的状态目录。落在其中任何一处的一次注入，会在 agent 每次启动时重新加载。随着更多 agent 状态熬过会话，我们受到经典的「后渗透」意义上新型持久化机制的威胁。会话启动时良好的分类器需要变得更普遍。多 agent 信任升级。一方面，子 agent 可以隔离不可信内容，向上层主 agent 返回结构化事实而非原始文本。另一方面，这也可能被滥用：如果子 agent 的输出被当成比原始工具结果更高的信任级别（因为这种输出来自「我们自己人」），就引入了一个新的 prompt injection 向量。在多 agent 系统里，分配不同信任级别与陷入信任升级之间，存在权衡。Agent 身份。Claude Cowork 对 agent 身份的回答很具体：凭证留在宿主钥匙串，VM 拿到一个按会话收窄权限的 token，而且这个 token 可以独立于用户被吊销。但我们才开始面对更宽的跨平台 agent 身份问题：agent 应该拥有自己的主体身份，还是应该作为用户的延伸、继承用户的权限？最终答案或许是两者的混合。随着 agent 能力变强，攻击面在不断移动。我们见过的失败类型，很可能也会在各行业、各实验室重演。我们需要集体投入 agent 专属的安全姿态，从共享基准、披露规范，到通用身份标准、跨厂商红队。

我们在本文聚焦围堵，但那只是 agent 安全图景的一部分。关于治理、可观测性和其余技术栈，参见 NIST 的 AI agent 身份与授权项目、由澳大利亚 ACSC 牵头、CISA 与英国 NCSC 参与的六机构 agentic AI 采用指南，以及 AI 管理体系标准 ISO/IEC 42001。我们的 Glasswing 倡议是其中一份贡献，但我们期待与伙伴乃至竞争对手就这一关键议题合作。

总结。简而言之，有几条我们反复回到的原则：先在环境层为围堵做设计，再在模型层引导行为。给我们教训最深的两起事故——员工钓鱼、以及第三方白名单披露——都是「出口」案例，数据经由一条被允许的通道离开。在每一例里，模型层都帮不上忙，因为没有异常可抓。当一切概率性防御都漏掉时，撞上的是那道确定性边界。让隔离强度匹配用户的监督能力。一个读得懂 bash 的开发者，和一个读不懂的知识工作者，跑的不是同一个威胁模型。一个用户能否评估 agent 即将做什么，应当帮助决定围堵策略；而无论朝哪边答错——给专家太多摩擦，给非专家太多信任——本身都是一种失败。警惕自研组件。久经考验的 hypervisor、系统调用过滤器、容器运行时，承受过的对抗性关注，远超你将自建的任何东西。在本文描述的每一处部署里，标准原语都站住了，而我们围绕它们自建的部分暴露了缺陷。最终，尽管 agent 可能是软件的新品类，它们系统层面的交互并非如此。它们仍然读文件、开 socket、生进程；这让用成熟工具做围堵成为一项关键且可行的防御。部署的风险收益平衡会随 AI 发展持续移动，但给破坏半径设一道硬上限，往往能把那道平衡推向正确的方向。

（作者：Max McGuinness、Mikaela Grace、Jiri De Jonghe、Jake Eaton、Abel Ribbink 等；脚注：Claude Code auto 模式把命令批准委托给基于模型的分类器，以极小摩擦为代价（约 0.4% 的正常命令被拦），漏掉一小部分危险动作（约 17% 的过度冒进行为会通过），所以它是沙箱内纵深防御的一层，而非替代品。）

**Anthropic Engineering：近期 Claude Code 质量报告的复盘更新**
1) 中文总结：Anthropic 承认过去一个月部分用户感觉 Claude Code「变笨了」，根因是三组互不相干的改动叠加（默认推理力度 high→medium、闲置会话清思考的缓存 bug、以及一条压低输出的系统提示），各自影响不同流量切片，合起来像「全面退化」。三者都已修复（截至 4 月 20 日 v2.1.116），4 月 23 日起为全体订阅者重置用量额度。文章坦诚复盘了每个 bug 怎么漏过评审，并给出后续改进（内部用公开构建版、加强 Code Review、系统提示改动要跑全模型评测 + 灰度）。
2) 中文全文翻译：
过去一个月，我们一直在调查「部分用户感觉 Claude 的回答变差了」的报告。我们把这些报告追溯到三个分别影响 Claude Code、Claude Agent SDK 和 Claude Cowork 的改动。API 未受影响。截至 4 月 20 日（v2.1.116），这三个问题都已解决。本文说明我们发现了什么、修了什么，以及我们会做出哪些不同，以确保类似问题更不容易再次发生。我们对退化类报告非常重视。我们从不故意劣化模型，也能立即确认我们的 API 和推理层未受影响。调查后，我们定位到三个不同的问题：3 月 4 日，我们把 Claude Code 的默认推理力度从 high 改成 medium，以减少某些用户在 high 模式下看到的、长到让 UI 仿佛卡死的延迟。这是个错误的取舍。在用户告诉我们他们更希望默认更高智能、并主动选择降低力度来做简单任务之后，我们于 4 月 7 日回滚了它。这影响了 Sonnet 4.6 和 Opus 4.6。3 月 26 日，我们上线了一个改动，清除那些闲置超过一小时的会话里 Claude 较早的「思考」，以降低用户恢复会话时的延迟。一个 bug 导致它不再是只清一次，而是在该会话余下的每一轮都清，这让 Claude 显得健忘、爱重复。我们在 4 月 10 日修好了。这影响了 Sonnet 4.6 和 Opus 4.6。4 月 16 日，我们在系统提示里加了一条指令来降低啰嗦程度。结合其他提示改动，它损害了编码质量，并在 4 月 20 日被回滚。这影响了 Sonnet 4.6、Opus 4.6 和 Opus 4.7。

因为每个改动在不同时间、影响了不同比例的流量，叠加后的整体效果看起来像大范围、不一致的退化。尽管我们从 3 月初就开始调查这些报告，但一开始它们很难和用户反馈的正常波动区分开，我们的内部使用数据和评测起初都没能复现这些问题。这不是用户应该从 Claude Code 得到的体验。截至 4 月 23 日，我们正在为所有订阅者重置用量额度。

关于 Claude Code 默认推理力度的改动：2 月我们在 Claude Code 里发布 Opus 4.6 时，把默认推理力度设为 high。不久后我们收到反馈：Opus 4.6 在 high 力度下偶尔会思考过久，导致 UI 看似卡死，并给那些用户带来不成比例的延迟和 token 消耗。一般来说，模型思考越久，输出越好。力度级别就是 Claude Code 让用户设定「思考多 vs 延迟低、用量省」这一取舍的方式。在校准力度时，我们会把这道取舍考虑进去，在 test-time-compute 曲线上挑出能给人们最佳选项范围的点；在产品层，我们再选曲线上哪一点作为默认，并以 effort 参数发给 Messages API，其余选项通过 /effort 提供。在我们的内部评测里，medium 力度在多数任务上只丢了少许智能，却显著降低了延迟，也不会出现 high 模式下偶发的超长尾延迟，还能最大化用户的用量额度。于是我们把默认改成 medium，并在产品内弹窗解释了理由。上线后不久，用户开始反映 Claude Code 变笨了。我们做了好几轮设计迭代，让当前的力度设置更显眼（启动提示、内联力度选择器、把 ultrathink 请回来），但多数用户还是保留了 medium 默认。在听到更多客户反馈后，我们于 4 月 7 日推翻了这个决定。现在所有用户默认：Opus 4.7 用 xhigh 力度，其余模型用 high 力度。

一个丢掉了先前推理的缓存优化：当 Claude 推理一个任务时，那段推理通常会保留在对话历史里，这样后续每一轮 Claude 都能看到它为什么做了那些编辑和工具调用。3 月 26 日，我们上线了一个本应提升该特性效率的改动。我们用 prompt caching 让用户连续的 API 调用更便宜更快。Claude 发起 API 请求时把输入 token 写进缓存，闲置一段时间后该 prompt 会被逐出缓存、给别的 prompt 腾地方。缓存利用率是我们仔细管理的。设计本该很简单：如果一个会话闲置超过一小时，我们可以清掉旧的思考段，以降低用户恢复该会话的成本——反正这次请求注定是缓存未命中，我们可以裁剪掉请求里不必要的消息，减少发给 API 的未缓存 token，之后恢复发送完整推理历史。为此我们用了 clear_thinking_20251015 这个 API header，配 keep:1。实现上有个 bug：它不是只清一次，而是在该会话余下的每一轮都清。一旦会话越过闲置阈值一次，该进程后续每个请求都告诉 API 只保留最新一块推理、丢弃之前全部。这会叠加：如果你在 Claude 正用工具时发了一条后续消息，那会在坏标记下开启新一轮，于是连当前轮的推理都被丢掉。Claude 会继续执行，却越来越不记得自己为什么选了那些动作。这表现为人们报告的健忘、重复和奇怪的工具选择。因为后续请求会不断丢掉思考块，那些请求也都成了缓存未命中。我们认为这正是「用量额度比预期消耗更快」这一独立报告的成因。两个不相关的实验让我们一开始很难复现：一个是仅内部的服务端消息队列实验；另一个是我们在「如何展示思考」上的正交改动，它在多数 CLI 会话里抑制了这个 bug，所以即便测试外部构建版我们也没抓到。这个 bug 处在 Claude Code 上下文管理、Anthropic API 和 extended thinking 三者的交叉点上。它引入的改动绕过了多轮人工与自动化代码评审，以及单元测试、端到端测试、自动化验证和内部试用。再加上它只发生在边角情况（陈旧会话）且难以复现，我们花了一周多才发现并确认根因。作为调查的一部分，我们用 Opus 4.7 对涉事 pull request 做了 Code Review 回溯。当提供能收集完整上下文所需的代码仓库时，Opus 4.7 找到了这个 bug，而 Opus 4.6 没有。为防止再犯，我们现在正在落地「让 Code Review 支持更多仓库作为上下文」。我们在 4 月 10 日 v2.1.101 修好了这个 bug。

一条降低啰嗦度的系统提示改动：我们最新的模型 Claude Opus 4.7 相比前代有个明显的行为怪癖：正如发布时写的，它倾向于相当啰嗦。这让它在难题上更聪明，但也产出更多输出 token。在发布 Opus 4.7 前几周我们就开始为 Claude Code 调优。每个模型行为略有不同，我们会在每次发布前花时间为其优化 harness 和产品。我们有多种降低啰嗦度的工具：模型训练、提示工程、以及改进产品里的思考 UX。最终这些我们都用了，但系统提示里新增的一条对 Claude Code 的智能影响过大：「长度限制：工具调用之间的文字保持在 ≤25 词。除非任务需要更多细节，最终回答保持在 ≤100 词。」在内部测试数周、且我们跑的那组评测没有回归之后，我们对这个改动有了信心，并在 4 月 16 日随 Opus 4.7 一起上线。作为本次调查的一部分，我们用更广的一组评测做了更多消融（从系统提示里删行以理解每行的影响）。其中一项评测显示 Opus 4.6 和 4.7 都掉了 3%。我们作为 4 月 20 日发布的一部分立即回滚了那段提示。

后续：为避免再出这类问题，我们会做些改变：确保更大比例的内部员工使用与公众完全一致的 Claude Code 公开构建版（而不是我们用来测新功能的版本）；改进我们内部使用的 Code Review 工具，并把改进版发给客户。我们还会对系统提示改动加更紧的控制：每次 Claude Code 的系统提示改动都会跑一套按模型划分的广泛评测、持续做消融以理解每行影响，并且我们造了新工具让提示改动更易审阅和审计。我们还在 CLAUDE.md 里加了指引，确保「针对特定模型」的改动只对该目标模型生效。对任何可能以智能为代价的改动，我们都会加入 soak 期、更广的评测套件和灰度发布，以便更早抓到问题。我们最近在 X 上创建了 @ClaudeDevs，以便深入解释产品决策及其背后的理由。我们也会在 GitHub 的集中帖子里同步同样的更新。最后，我们要感谢用户：那些用 /feedback 命令向我们反馈问题（或在网上贴出具体、可复现的例子）的人，最终让我们得以定位和修复这些问题。今天我们正在为所有订阅者重置用量额度。我们非常感谢你们的反馈与耐心。

**Anthropic Engineering：扩展托管 Agent——把「大脑」与「手」解耦**
1) 中文总结：Anthropic 介绍 Claude Managed Agents——一个在 Claude Platform 上代跑长程 agent 的托管服务。核心设计哲学是「把大脑（Claude + harness）与手（沙箱 / 工具）和会话（事件日志）解耦」，各自成为接口、可独立替换与失败。文章讲清了「别养宠物（pet），要养牲口（cattle）」的运维教训、解耦后安全边界（凭证永不进沙箱）、以及把会话日志当作「活在上下文窗口之外的上下文对象」如何把 p50 首 token 延迟（TTFT）降约 60%、p95 降超 90%。
2) 中文全文翻译：
按我们的文档上手 Claude Managed Agents。工程博客一个持续的主题是如何构建高效的 agent、以及如何为长时任务设计 harness。这些工作的一个共同主线是：harness 把「Claude 自己做不到什么」的假设编码了进去。但这些假设需要被经常质疑，因为随着模型变强它们会过时。举个例子：此前我们发现 Claude Sonnet 4.5 会在感知到上下文快到上限时过早收尾任务——这种行为有时被称为「上下文焦虑」。我们通过给 harness 加上下文重置来解决。但当我们把同一套 harness 用在 Claude Opus 4.5 上时，发现那个行为消失了，重置变成了累赘。我们预期 harness 会持续演进。所以我们造了 Managed Agents：Claude Platform 上的一个托管服务，通过一小套「意图活得比任何具体实现更久」的接口（包括我们今天在跑的那些）代你跑长程 agent。造 Managed Agents 等于解决计算领域一个老问题：如何为一个「尚未被设想出来的程序」设计系统。几十年前，操作系统通过把硬件虚拟化成抽象——进程、文件——来解决这个问题，这些抽象足够通用，能容纳还不存在的程序。抽象活得比硬件久。read() 命令不关心它访问的是 1970 年代的磁盘组还是现代 SSD。上层抽象保持稳定，下层实现自由更替。Managed Agents 遵循同样的模式。我们把 agent 的组件虚拟化：一个会话（发生的一切的只追加日志）、一个 harness（调用 Claude、并把 Claude 的工具调用路由到相关基础设施的循环）、以及一个沙箱（Claude 能跑代码、改文件的执行环境）。这让每一块的实现都能被替换而不扰动其他块。我们对这些接口「长什么样」有主张，但对它们背后跑什么没有。

别养宠物。我们一开始把 agent 的所有组件放进同一个容器，意味着会话、harness 和沙箱共享同一环境。这种做法有好处：文件编辑是直接系统调用，也没有要设计的服务边界。但把一切都耦合进一个容器，我们撞上了一个老基础设施难题：我们养了一只宠物（pet）。在「宠物 vs 牲口」类比里，宠物是命名、手工照料的个体，你输不起；牲口则可互换。我们的案例里，那台服务器成了那只宠物：容器一挂，会话就没了；容器无响应，我们还得把它「护理」回健康。护理容器意味着调试卡住的会话。我们唯一的窗口是 WebSocket 事件流，但它说不清故障出在哪，于是 harness 里的 bug、事件流里的丢包、还是容器离线，表现全都一样。要弄清出了什么错，工程师得进容器里开个 shell，但因为那容器往往也装着用户数据，这种做法本质上意味着我们丧失了调试能力。第二个问题是，harness 假设 Claude 处理的任何东西都和它同处一个容器。当客户要我们把 Claude 接到他们的虚拟私有云时，他们要么把网络和我们对等互联，要么在我们的环境里跑 harness。一个烤进 harness 的假设，在我们要把它接到不同基础设施时成了问题。

把大脑与手解耦。我们想到的解法是：把「大脑」（Claude 及其 harness）从「手」（执行动作用的沙箱和工具）和「会话」（会话事件的日志）解耦。每一块都变成一个对彼此少做假设的接口，且每一块都能独立失败或被替换。harness 离开容器。把大脑与手解耦意味着 harness 不再住在容器里。它调用容器的方式，和它调用任何其他工具一样：execute(name, input) → string。容器变成了牲口。容器死了，harness 就把失败当成一个工具调用错误、回传给 Claude。如果 Claude 决定重试，就可以用标准配方重初始化一个新容器：provision({resources})。我们不再需要把挂掉的容器护理回健康。

从 harness 失败中恢复。harness 也变成了牲口。因为会话日志在 harness 之外，harness 里没有任何东西需要在崩溃后存活。当一个挂了，新的可以用 wake(sessionId) 重启，用 getSession(id) 取回事件日志，并从最后一个事件续上。在 agent 循环里，harness 用 emitEvent(id, event) 写会话，以保留一份持久的事件记录。

安全边界。在耦合设计里，Claude 生成的任何不可信代码都和凭证跑在同一个容器里——所以一次 prompt injection 只需要说服 Claude 去读它自己的环境。攻击者一旦拿到那些 token，就能拉起全新、不受限的会话并把活派给它们。收窄 scope 是个显然的缓解，但这等于把「Claude 拿受限 token 干不了什么」的假设烤了进去——而 Claude 正越来越聪明。结构性的修法是：确保 token 在任何情况下都从「Claude 生成代码所跑的沙箱」够不着。我们用了两种模式来保证这一点。鉴权可以和一个资源捆绑，也可以放在沙箱外的保险库里。对 Git，我们在沙箱初始化时用每个仓库的访问 token 去 clone，并接进本地 git remote。git push / pull 在沙箱内就能工作，agent 从不需要经手 token 本身。对自定义工具，我们支持 MCP，并把 OAuth token 存在安全保险库里。Claude 通过一个专用代理调用 MCP 工具；该代理接收一个与会话关联的 token，再从保险库取对应凭证、向外部服务发起调用。harness 永远不该知道任何凭证。

会话不是 Claude 的上下文窗口。长程任务常常超出 Claude 上下文窗口的长度，而标准的应对办法都要对「保留什么」做不可逆的决定。我们在之前的上下文工程工作里探索过这些技术。比如，compaction 让 Claude 存一份上下文窗口的摘要，memory 工具让 Claude 把上下文写进文件，实现跨会话学习。这可以和上下文裁剪搭配，选择性地移除旧工具结果或思考块等 token。但对「有选择地保留或丢弃」的不可逆决定会导致失败——很难知道未来的轮次会需要哪些 token。如果消息被 compaction 步骤转换过，harness 会把被压缩的消息从 Claude 的上下文窗口移除，而它们只有在被存下来时才可恢复。先前的工作探索过把上下文存成「活在上下文窗口之外的对象」来解决这一点。比如，上下文可以是 REPL 里的一个对象，LLM 通过写代码来过滤或切片、以编程方式访问它。在 Managed Agents 里，会话提供同样的好处，充当「活在 Claude 上下文窗口之外」的上下文对象。但上下文不是存在沙箱或 REPL 里，而是持久存在会话日志里。接口 getEvents() 让大脑能通过选取事件流的位置切片来查询上下文。这个接口用起来很灵活：大脑可以从它上次停读的地方接着读，在某个特定时刻前回退几个事件看前因，或在某个特定动作前重读上下文。任何取回的事件也可以在进 Claude 上下文窗口前，先经 harness 转换。这些转换可以是 harness 编码的任何东西，包括为拿到高 prompt 缓存命中率而做的上下文整理，以及上下文工程。我们把「会话里可恢复的上下文存储」与「harness 里任意的上下文管理」这两件事分开，是因为我们预测不了未来模型会需要哪种具体的上下文工程。接口把那个上下文管理推进 harness，只保证会话是持久的、且可被查询的。

多大脑，多双手。多大脑：把大脑与手解耦，解决了我们最早的一批客户投诉之一。当团队想让 Claude 打他们自己 VPC 里的资源时，唯一的路是和我们对等互联网络，因为装 harness 的容器假设每个资源都挨着它。一旦 harness 不在容器里，那个假设就消失了。同一改动还带来了性能回报。我们起初把大脑放进容器，意味着「多少个大脑就要多少个容器」。对每个大脑，在容器就绪前都无法推理；每个会话都预先支付完整的容器搭建成本。每个会话，哪怕永远不碰沙箱，也得 clone 仓库、拉起进程、从我们服务器取待处理事件。那段死等时间体现在 time-to-first-token（TTFT，首 token 延迟）上——这是用户感受最尖锐的延迟。把大脑与手解耦意味着：容器只在需要时由大脑通过工具调用（execute(name, input) → string）来供给。所以一个不马上需要容器的会话不用等容器。编排层一旦从会话日志取回待处理事件，推理就能开始。用这套架构，我们的 p50 TTFT 大约降了 60%，p95 降了超过 90%。扩展到多大脑，只是启动多个无状态 harness、并在需要时把它们连到手。多双手：我们也想要把每个大脑连到多双手的能力。实践中，这意味着 Claude 必须推理多个执行环境、并决定把活派去哪——这比在单个 shell 里操作更难。我们最初把大脑放在单个容器里，是因为早前的模型没这能力。随着智能提升，单个容器反而成了限制：那个容器一挂，大脑正伸向的每只手的状态都丢了。把大脑与手解耦，让每只手都成为一个工具 execute(name, input) → string：名字和输入进去，字符串回来。这个接口支持任何自定义工具、任何 MCP server、以及我们自己的工具。harness 不知道沙箱是容器、手机还是宝可梦模拟器。而且因为没有哪只手耦合到任何大脑，大脑之间还能把手互相传递。

结论：我们面对的挑战是个老问题——如何为「尚未被设想出来的程序」设计系统。操作系统靠把硬件虚拟化成足够通用的抽象，活了几十年。借助 Managed Agents，我们旨在设计一个能容纳 Claude 周围未来 harness、沙箱或其他组件的系统。Managed Agents 是同一种精神的元 harness（meta-harness），对 Claude 未来需要的那个具体 harness 不做主张。它是一套带通用接口、能容纳许多不同 harness 的系统。比如 Claude Code 就是一个我们广泛用于各类任务的优秀 harness；我们也展示过任务专属的 agent harness 在窄域里表现出色。Managed Agents 能容纳其中任何一个，随时间匹配 Claude 的智能。元 harness 设计意味着对 Claude 周围的接口有主张：我们预期 Claude 需要操控状态（会话）和进行计算（沙箱）的能力，也需要扩展到多大脑、多双手的能力。我们设计这些接口，让它们能在长时段里可靠、安全地运行。但我们对 Claude 需要多少、在哪的大脑或手，不做任何假设。

（作者：Lance Martin、Gabe Cemaj、Michael Cohen 等。）
