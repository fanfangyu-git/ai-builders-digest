**Anthropic：在 Apple 平台上用 Foundation Models framework 接入 Claude**
1) 中文总结：Anthropic 发布了一个新的 Swift package，让 Apple 开发者可以通过 Apple 的 Foundation Models framework 调用 Claude，处理多步推理、代码生成等复杂工作流。思路是"各司其职"：设备端模型负责摘要、抽取这类快而本地的任务；当请求需要多步推理时，再把任务移交给 Claude，Claude 还能联网搜索最新信息、跑代码做数据分析，并以流式方式把结果回到同一视图。该支持明天上线，覆盖 iOS 27 / iPadOS 27 / macOS 27 / visionOS 27 / watchOS 27，开发者用 Anthropic API key 登录即可，package 会处理流式输出、工具调用和结构化返回。
2) 中文全文翻译：今天，我们通过一个新的 Swift package 发布了对 Claude 的 Foundation Models framework 支持，让 Apple 开发者能够借助 Apple 的 Foundation Models framework 来调用 Claude，处理更复杂的工作流。Apple 的 Foundation Models framework 让开发者可以直接从 Swift 原生调用模型。它用起来非常简单，通过引导式生成（guided generation），最少三行代码就能返回带类型的 Swift 值。开发者可以用它调用 Apple 设备端模型，处理摘要、抽取这类快速、本地的任务。当某个请求需要多步推理、代码生成等能力时，开发者现在可以用 Apple 的 Foundation Models framework 把任务移交给 Claude。Claude 还能联网搜索最新信息，并执行代码来做数据分析。Claude 的回复会以流式方式回到同一个视图里。因为 Apple 的 framework 会通过 @Generable 注解返回带类型的值，开发者在调用 Claude API 时拿到的是干净的结构化输入，而不是原始的用户文本。

这解锁了什么？Foundation Models framework 已经驱动了一系列智能设备端功能，比如能给出个性化提示的日记类 app、能总结合同的文档类 app、能按学生水平讲解概念的学习类 app。加上 Claude 之后，每一种模式都被延伸了。一个日记 app 可以在设备端生成每日提示，再让 Claude 去跨数月的内容里找出线索脉络；一个学习 app 可以在设备端先定义一个术语，等学生追问"这对我们讲过的其他内容有什么意义"时，再把问题移交给 Claude。对用户来说这是同一个体验，而背后每一步都由最合适的模型支撑。

如何上手？Claude 对 Foundation Models framework 的支持将于明天上线，并通过 Apple 的 Foundation Models framework 在 iOS 27、iPadOS 27、macOS 27、visionOS 27 和 watchOS 27 上运行。把它加入你的项目，用 Anthropic API key 登录，再把 Apple 设备端生成的带类型输出传进一个 Claude 请求，剩下的交给这个 package：它会处理流式输出、工具调用，以及把结构化响应返回到你的 SwiftUI 视图里。
3) 推荐理由：这是 Apple 端侧智能 + 云端 Claude 的一次官方打通，对做 Apple 平台 AI app 的开发者是直接可用的能力；也印证了"端侧小模型做快任务、云端大模型做难任务"的混合架构正在成为主流。

**Mitch Troyanovsky（Basis 联合创始人）：如何构建长周期 AI Agent**
1) 中文总结：本期核心结论——做长周期自主 agent 的关键，不是追求单次结果的惊艳，而是把"可信、可控、可审查"的流程工程化。Basis 的 agent 能自主运行数小时甚至数天，端到端完成报税这类复杂工作。Mitch 把长周期 agent 定义为"被授予在更长时间内保持连贯（coherent）决策权的系统"，并指出 LLM 有巨大的工作记忆、却没有短期或长期记忆，必须靠 harness 和"写笔记"（他拿电影《记忆碎片》作类比）来维持跨步连贯。最反直觉的判断是：别只信结果评测——100 个 eval 全过也不代表能泛化到生产；就像一个人 100 次都答对了，但如果只是靠查维基百科，会计所也不会雇他，所以也不该雇这个 AI。Basis 因此引入 "behavior specs"（写进 markdown 的行为规范，既是 spec 也是 rubric），要求 agent 引用一手来源、交稿前自检等，并强调要"用人类组织如何工作"来设计 agent 系统。他还认为 coding 先跑通，是因为运行时易验证、训练数据质量高，而非只会靠可验证奖励（verifiable rewards）；在模型史上看，Opus 3 是被低估的"首个真正理解长上下文"的模型，o1/o3 才是推理范式的真正突破，且自 o3 后没有范式级变革。
2) 推荐理由：如果你在做多步 agent 产品或研究，这期几乎是一份"长周期 agent 工程手册"。Mitch 把抽象问题（记忆、评测、可信部署）落到可操作原则（behavior specs、过程优于结果、少而精的行为约束），并诚实说出"你不需要 Move 37，你需要的是可被组织信任的可靠性"——对想让 agent 真正进生产环境的人非常解渴。

**节译 1 — 上下文比代码更重要**
> 你会看到有人为了一个没抽象好的代码文件抓狂，可他们给的上下文却一塌糊涂。英文（提示 / 上下文）更珍贵，因为它直接影响表现；代码本身不影响表现。

**节译 2 — 为什么不能只信结果评测**
> 假设你有 100 个 eval，全过了，看起来不错。那你能确信它现在已经能泛化到真实世界、泛化到生产环境了吗？我们的答案是否定的。哪怕一个人 100 次里有 100 次都答对了，如果那个人只是靠查维基百科答对，会计所也不会雇他，所以也不该雇我们。

**核心要点清单**
- 长周期 agent = 被授权在长时间内保持决策连贯的系统；LLM 缺记忆，要靠 harness + "写笔记"（状态外置）维持连贯。
- 评测要"过程优先于结果"：只看过关的结果 eval 会漏掉"靠查维基百科答对"的不可信路径；behavior specs（markdown 行为规范）既是规范也是评分 rubric，要引用一手来源、交稿前自检。
- behavior specs 越少越好：只保留那些泛化性最强、对生产影响最大的少数几条，避免维护负担。
- coding 先跑通 = 运行时易验证 + 文本化 + 高质量训练数据；但"编码是门艺术"，可验证奖励解决不了 taste。
- 给困难步骤加算力：难的问题可并行 spawn 多个子 agent 投票；越长的轨迹越需要"子 agent + 压缩"来维持上下文。
- "魔法盒子 / 外星人"心智模型：把模型当成一个能在推断时学习推理的黑盒，结合组织设计的基本原则，就是当下 agent 构建的前沿。
- 建立 LLM 直觉的最好方式不是刷论文或推特，而是在自己的真实工作里大量使用它、去找"到底卡在哪"的瓶颈（Elon 式第一性原理）。
