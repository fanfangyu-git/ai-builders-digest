**Anthropic 工程博客 —《关于近期 Claude Code 质量反馈的说明》（事故复盘）**
1) 中文总结：过去一个月里，部分用户反馈 Claude 的回答质量变差。Anthropic 复盘后确认问题源自三个**互相独立**的改动，影响范围是 Claude Code、Claude Agent SDK 和 Claude Cowork，**API 未受影响**；三个问题均已在 4 月 20 日（v2.1.116）修复。官方明确表示「我们从不故意降级模型」，并在 4 月 23 日为所有订阅用户重置了用量额度。
2) 三个根因（要点梳理）：
- **默认推理强度被下调**：3 月 4 日把 Claude Code 的默认 reasoning effort 从 high 降到 medium，本意是缓解 high 模式下偶发的超长延迟（久到 UI 看起来像卡死）。官方承认「这是个错误的取舍」，4 月 7 日回滚。现在 Opus 4.7 默认 xhigh，其他模型默认 high。影响 Sonnet 4.6 / Opus 4.6。
- **缓存优化误删历史思考**：3 月 26 日上线一个优化——对空闲超过 1 小时的会话，清理旧的 thinking 段落以降低恢复成本。但 bug 导致这个清理在该会话的后续**每一轮**都反复执行，而非只做一次，于是 Claude 显得「记性差、爱重复」。4 月 10 日修复。影响 Sonnet 4.6 / Opus 4.6。
- **减少啰嗦的系统提示反噬**：4 月 16 日加入一条「降低冗长度」的系统提示指令，与其他 prompt 改动叠加后损害了编码质量，4 月 20 日回滚。影响 Sonnet 4.6、Opus 4.6、Opus 4.7。
- **为何难以察觉**：三个改动分别影响不同的流量切片、且时间表各不相同，叠加后在外部看起来就像「大范围、不稳定的整体降级」。官方从 3 月初开始调查，但初期难以与用户反馈的正常波动区分，内部使用和 evals 一开始也没能复现。
3) 推荐理由：这是一份罕见坦诚的 AI 产品事故复盘，对所有做 LLM 产品的人都是教材级案例——**延迟与智能的取舍不要替用户默默做决定**、缓存优化可能悄悄破坏上下文完整性、以及「减少啰嗦」这类无害的 prompt 微调也可能连带损害核心能力。同时它解释了社区长期争论的「模型是不是偷偷变笨了」：这次确有其事，但原因在产品层而非模型层。
4) 原文链接：https://www.anthropic.com/engineering/april-23-postmortem

**Anthropic 工程博客 —《扩展 Managed Agents：把「大脑」与「双手」解耦》**
1) 中文总结：文章从一个核心观点出发——harness（驱动 agent 的外层循环）本质上编码了「Claude 自己做不到什么」的假设，而随着模型变强，这些假设会**过期**。举例：Sonnet 4.5 会因为感知到上下文上限将近而提前草率收尾（业内称「context anxiety」），他们为此在 harness 里加了 context reset；但换到 Opus 4.5 上这个行为消失了，那些 reset 就变成了纯粹的累赘。因此他们构建了 Managed Agents——Claude Platform 上的托管服务，用一小组「能比任何具体实现活得更久」的接口来跑长周期 agent。
2) 架构要点（要点梳理）：
- **借鉴操作系统的抽象思路**：几十年前操作系统把硬件虚拟化成 `process`、`file` 这类足够通用的抽象，从而支撑「尚未被构想出来的程序」；`read()` 不关心底下是 1970 年代的磁盘还是现代 SSD。Managed Agents 同样把 agent 的组件虚拟化成三者：**session**（记录一切发生过的事的只追加日志）、**harness**（调用 Claude 并把工具调用路由到相应基础设施的循环）、**sandbox**（Claude 执行代码和改文件的环境），三者实现可互换而互不干扰。
- **「不要养宠物」**：最初把 session、harness、sandbox 全塞进同一个容器，好处是文件编辑就是直接系统调用、没有服务边界要设计；但这让服务器变成了「宠物」（pets vs cattle 类比中那个不能丢、要精心照料的个体）——容器一挂，会话就没了；容器无响应就得「救活」它。更糟的是唯一的观测窗口只有 WebSocket 事件流，harness 的 bug、事件流丢包、容器掉线三种故障看起来一模一样；要排查就得进容器开 shell，但容器里往往还装着用户数据，于是实际上等于没有调试能力。
- **把大脑从双手上摘下来**：harness 移出容器，像调用任何其他工具那样调用容器：`execute(name, input) → string`。容器于是变成了「牛」——挂了就当工具调用报错抛回给 Claude，Claude 若决定重试，就用标准配方 `provision({resources})` 重开一个。
- **harness 自身也变成牛**：因为 session 日志放在 harness 外部，harness 里没有任何东西需要在崩溃中存活；崩了就用 `wake(sessionId)` 重启一个，用 `getSession(id)` 取回事件日志，从最后一个事件继续。agent 循环运行期间用 `emitEvent(id, event)` 写入 session 以保持持久记录。
- **安全边界**：在耦合设计里，Claude 生成的不受信任代码与凭据跑在同一个容器中，因此一次 prompt injection 只需说服 Claude 去读自己的环境变量就够了——解耦后这条路被切断。
3) 推荐理由：这是目前关于「长周期 agent 该怎么架构」最实在的一篇工程文章。两个观点可以直接拿走：① **harness 里的每个补丁都是对模型缺陷的假设，模型升级后要主动删代码**，否则就是技术债；② 用 pets-vs-cattle 和操作系统抽象来设计 agent 基础设施，把 session/harness/sandbox 三者解耦，既能获得容错，也顺带解决了「凭据与不受信任代码同处一室」的安全问题。
4) 原文链接：https://www.anthropic.com/engineering/managed-agents

**claude.com 博客 —《Claude Managed Agents 新功能：自托管沙箱与 MCP 隧道》（2026-05-19）**
1) 中文总结：Managed Agents 现在可以在**你自己控制的沙箱**里执行工具，并连接到你**私有网络内的 MCP 服务器**。也就是说，agent 执行工具的沙箱、以及它访问的服务，都可以运行在企业既有的安全与运行时边界之内。沙箱可以跑在自有基础设施上，也可以交给 Cloudflare、Daytona、Modal、Vercel 这类托管方处理算力与隔离。目前自托管沙箱为 public beta，MCP 隧道为 research preview（需申请）。
2) 要点梳理：
- **自托管沙箱**：编排、上下文管理、错误恢复这些 agent 循环仍留在 Anthropic 的基础设施上，而**工具执行搬到你自己配置的环境**里。代码执行、敏感文件、依赖包、服务与数据都留在企业边界内，沿用你已有的网络策略、审计日志和安全工具，文件与代码仓库不外流。算力也由你掌控——资源规格和运行时镜像都在你这边设定，长时间构建、图像生成这类重计算任务能拿到所需的 CPU、内存和容量。
- **四家支持的沙箱方各有侧重**：Cloudflare 用 microVM 与更轻量的 isolates 大规模运行沙箱，出站请求可控（零信任密钥注入、可自定义代理用于审计/改写/重路由出口流量、可通过其网络连内部服务）；Daytona 的沙箱是「完整可组合的计算机」，长时运行且有状态，会话期间可通过 SSH 或带认证的预览 URL 访问，也可暂停并完整恢复状态；Modal 的沙箱与其函数、存储、网络原语同源，自定义容器运行时可在任意镜像上做到亚秒级启动，能扩展到数十万并发沙箱，CPU/GPU 按需供给；Vercel 沙箱结合了 VM 级安全、VPC peering 和 bring-your-own-cloud，毫秒级启动，且由沙箱防火墙在网络边界注入凭据，**凭据永不进入沙箱内部**。
- **已落地的客户案例**：Amplitude 基于 Managed Agents + Cloudflare 构建内部的 Design Agent（用于符合品牌规范的生产级 UI 与营销设计）；Clay 的 GTM 工程 agent「Sculptor」在 Managed Agents + Daytona 上自主构建、测试并监控工作流；服务机构投资金融的 AI 平台 Rogo 基于 Managed Agents + Vercel Sandbox 构建分析师 agent 以安全处理专有数据。
- **MCP 隧道**：让 Managed Agents 连上私有网络内的 MCP 服务器而**无需将其暴露到公网**——内部数据库、私有 API、知识库、工单系统都能变成 agent 可调用的工具。你部署一个轻量网关，它只发起**单向出站连接**，不需要任何入站防火墙规则、没有公网端点、流量端到端加密。Managed Agents 与 Messages API 均支持，由组织管理员在 Claude Console 的 workspace 设置中管理。
3) 推荐理由：这基本上是「企业为什么迟迟不敢上 agent」的正面回答——数据不出域、凭据不进沙箱、内部服务不暴露公网。如果你在推动企业内部落地 agent，这三条正是安全与合规团队最常卡住的点；另外「控制面（agent 循环）托管 + 数据面（工具执行）自持」的拆分方式，也值得任何做 B 端 AI 平台的团队参考。
4) 原文链接：https://claude.com/blog/claude-managed-agents-updates

## 播客

**AI & I（主持人 Dan Shipper）×  Kevin Scott（微软 CTO）—《微软对「为 agent 而生的互联网」的构想》（Best of the Pod 重播）**
1) 中文总结：这期对话围绕「agentic web（agent 化的互联网）」展开。Kevin Scott 首先解释了叙事重心的变化：去年大家还在怀疑 scaling laws 会不会失效，如今已连年证明其依然有效，不再需要反复提醒；而真正值得谈的是他称之为「**capability overhang（能力悬垂）**」的现象——模型的推理能力已经跑在产品实际交付的能力之前，整个行业都还需要补上这段差距。他认为要让 agent 真正有用，光靠推理能力不够，还有一堆事情要理顺：一是 **agent 记忆**目前受限，agent 偏「事务性」，一个任务内记忆连贯、任务结束后可能就归零，下次从头开始，这严重限制了把越来越复杂的任务委派给它；二是 agent 必须能代表你**采取行动**——使用工具、修改系统、查询丰富多样的信息源，而要做好这件事，就需要一个「长得很像互联网」的生态：如果你已经有网站、有对外提供服务的 API，就得想办法把它接通，让 agent 能与之对话，并让各方的商业动机都对得上。
2) 核心观点梳理：
- **协议层类比**：MCP 在 agentic web 中扮演的角色，相当于互联网上的 HTTP；NLWeb 则大致相当于 HTML。他期待这类「简单、可组合、可分层」的开放协议大量涌现并走向普及，agent 才真的能干事。
- **不要把组织架构图当产品交付**：作为 CTO，他在微软内部推动的一件事是「让所有内部系统用**同一套标准协议**与我们自己写的所有 agent 对话」，以免把康威定律（Conway's law）暴露给整个世界——也就是俗称的「你交付的是你的组织架构图」。缺少标准协议与共享服务时，那种低效重复建设「看着就是一场恐怖片」。
- **MCP 的安全模型**：主持人指出互联网有同源策略之类的安全机制，而 MCP 没有对应物。Kevin 坦言自己也不确定正确答案是什么，但认为 MCP «足够连贯地简单»，社区因此相对容易达成共识。企业侧他们正与 MCP 团队推进的关键能力包括：给 agent **身份**以便构建授权（entitlement）体系，能声明「此 agent 代表某人行事、有权访问这些资源」；让 agent 能先去查询「我要做这件事需要碰哪些系统、需要申请哪些权限」，再向委派任务的用户请求许可（是/否）；以及让系统管理员对「这一切是否被允许」有掌控。他强调这些应当以**开放方式**实现，而不是绑定在某家的 agent 或系统上。
- **封闭垂直 vs 开放生态是「伪二分」**：面对「垂直整合能保证安全、开放生态利于创新」的经典取舍，他认为这可能是个假两难。开放系统的真正优势是**无需许可（permissionless）的创新**——你不必求得谁的批准才能把东西分发给别人；他认为过去几年冒出来的一些中间层，对「做出东西的人」和「愿意付出注意力或金钱去用它的人」这两方并没贡献多少价值。同时他相信可以借助 AI 自身获得更强的安全性：比如让一个了解你安全偏好与风险评估的 agent 照看你的多个通信渠道，察觉异常并交叉验证。他举了当天早上的亲身例子——他是妻子账号的备用安全联系人，收到一串两步验证被改动的邮件提醒后，他没有回邮件（担心邮箱已被入侵）而是**改用短信**去确认，结果是妻子本人在改配置；这类判断完全可以由 agent 来做。
- **关于「手艺」与工具之争**：他强调自己热爱「造物者」（不论是软件工程师、机械工程师、木工还是陶艺人）对如何做事有强烈主张——这是做到卓越的必要条件。他写第一个程序时 12 岁，编程已 41 年，见过软件开发方式的多次非平凡变化以及随之而来的激烈争论。他自嘲「我们自己做 VS Code，但我这个老顽固还在用 vi」，明知这在某些方面是次优选择，但他有权这么选；而在其他事情上他会判断「重要的不是过程而是结果」，那就选最强或最方便的路径，不在乎谁会因此扔石头。他用木工类比：少年时争论「用电动工具还算不算真木匠」，如今争论变成了「用 CNC 算不算」。差别源于**有人更看重过程、有人更看重结果**。他给的建议是：保留你对手艺的强烈主张，但在工具变化时保持开放心态——他自己拖了很久才去学 3D 打印，事后非常后悔，「早该开始」。总结成一句：保持好奇，去试，好用就用，不好用就别用。
- **agent 生态的未来形态**：不会有「一个 agent 统治所有」。他认为期待全世界每个开发者在工作的重要环节上都用同一个工具是不现实的——能自由选择、随意折腾正是做开发者的乐趣之一，而「人们不断更换工具」是他四十年里看到的最稳定的现象之一（微软自己也会努力竞争，让 GitHub Copilot 及相关 agent 成为很多人愿意选的工具）。至于 agent 之间的差异维度，他认为**最重要的是「做产品」那一部分**：他见到的最有意思的初创公司并不试图靠打造差异化基础设施来创新，而是因为自认为**对某个人的某个问题的理解胜过所有人**，然后拿现成基础设施去改造、调优，把自己理解的那个问题以世界级水准解决掉。正因为现在获得这种细致理解、并抄起工具去解决它的门槛低了太多，所以会涌现大量公司做大量东西。
- **一年后的预测**：那些还抱着「技术还没准备好」（试过一次，觉得稍微太贵、或稍微差点意思）当理由继续等待的人，会被落下很远，因为**每一年一切都会更便宜、也更有能力**。他说赌失败与赌乐观的代价差距是巨大的。他预期会看到人们用 agent 攻克的问题在**雄心量级**上大幅提升；而随着 agentic web 更完整、模型的推理与规划能力持续变强，交互模式会从**同步走向异步**——现在的典型用法是坐下来、发出 prompt、等它返回；而明年你会看到人们对 agent 说「去把这件事搞定」，agent 花很长时间、对外发出大量调用（那些被触发的动作本身也要等一阵才回来），整合所有响应、可能反复迭代多轮，然后在相当长一段时间之后告诉你「我做到这里了，轮到你了」。
3) 推荐理由：这是目前对「agent 时代的基础设施该长什么样」讲得最系统的一次高管访谈，而且几乎每个判断都能落到实操上：**capability overhang** 意味着当下最大的机会不在训模型而在把现有能力做进产品；**MCP ≈ HTTP、NLWeb ≈ HTML** 给了协议层选型的心理模型；agent 身份 + 授权体系 + 权限申请这套设计，正是企业级 agent 现在最缺的一块；而「差异化来自对问题的理解、不是基础设施」对创业者是明确的取向建议。与今天 Peter Yang 的「语音编排 + 计算上云」、Madhu Guru 的「alpha 在应用层」、Aaron Levie 的「降价催生需求」放在一起看，几位 builder 在完全不同的位置上指向了同一个结论。
4) 原文链接：https://www.youtube.com/playlist?list=PLuMcoKK9mKgHtW_o9h5sGO2vXrffKHwJL
